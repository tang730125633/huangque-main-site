# 黄雀主站 · 现有结构优化方案

> 生成日期：2026-07-03　|　依据：仓库 `huangque-main-site`（main @ d5bb768 + PR #27 同步分支）与生产服务器 129.204.166.13 实况对账
> 结论先行：**架构本身（静态前端 + 单文件 Python 微服务 + nginx 分发）适合当前团队规模，不建议推倒重来**；要优化的是 ①堵住安全/流程漏洞 ②给最大的单文件后端做拆分 ③消除前端重复与缓存隐患 ④仓库卫生。

## 二、问题清单与优化建议

### 🔴 P0 —— 安全与流程（先堵漏，半天内可完成）

#### P0-1 明文口令已提交进 git
`deploy/systemd/leadgen-A.service` / `leadgen-B.service` 里有：

```
Environment=LEADGEN_PASSWORD=DaPengAI@2026
Environment=LEADGEN_WORKER_TOKEN=worker-secret-2026
```

仓库虽是 private，但 git 历史永久保留，且 `scripts/crawl_cli.py` 里也写了同一默认口令。
**做法**：① 换新口令/新 token（旧的视为已泄露）；② 单元文件改用 `EnvironmentFile=/etc/huangque/leadgen.env`（该文件只放服务器，权限 600）；③ git 里的单元文件只留 `EnvironmentFile=` 引用。豆包/HeyGen/TikHub 凭证目前在服务器 unit 的 Environment 里、未进 git（正确），顺手一并迁到 EnvironmentFile 统一管理。

#### P0-2 双轨修改导致 git 与线上漂移
有人走 ship（git），有人直接在服务器上改（产生 60+ 个 `.bak.时间戳` 文件）。这次漂移已回收，但机制不改还会再漂。
**做法**：① 团队约定**唯一修改入口是 ship**，服务器上不再手改；② 加一个每日漂移哨兵（服务器 cron 跑 md5 对账脚本，本次对账用的方法已验证可行：`sed 's/\r$//' | md5sum` vs `git show HEAD:file`，不一致就发飞书/邮件告警）；③ 应急热改允许，但必须当天用 ship 流程补提交。

#### P0-3 备份文件污染
- 生产 webroot 里 100+ 个 `.bak.*`（`assets.html` 一个文件 60+ 份备份），nginx 可直接对外服务这些旧文件（`https://…/workbench/assets.html.bak.xxx` 能被猜访问，旧版可能含未修复漏洞）。
- git 里也跟踪着 `server/app.py.bak-comments`、`server/index.html.bak-tabfix`。

**做法**：服务器上 `.bak*` 全部挪到 `~/backups/webroot-bak-20260703/` 归档（git 已有完整历史，这些备份不再需要）；git 里两个 .bak 文件删除；nginx 加一条 `location ~ \.bak { deny all; }` 兜底。

#### P0-4 SSH 密码登录
运维用 `ubuntu` + 密码（本次我也是密码登入）。**做法**：给开发机配 ed25519 密钥（仓库 ship 脚本本来就假设 `~/.ssh/dapeng_server_ed25519`），然后 sshd 关闭 PasswordAuthentication。

### 🟠 P1 —— 后端结构（本周内，收益最大）

#### P1-1 `content_api.py` 拆分（1993 行，6 个业务域挤在一个文件）
一个文件同时管：点数计费、音色克隆（豆包）、TTS、作图、文案 LLM、HeyGen 视频、任务队列 + reaper 线程。每次只改音频也要重启整个服务，影响正在跑的视频任务。
**做法（不换框架，保持零依赖风格）**：按域拆成模块，`content_api.py` 只留 HTTP 路由与任务队列：

```
content-api/
├── content_api.py      # 路由 + Job 队列 + reaper（~400 行）
├── hq_common.py        # _post/_multipart/verify/points/db 工具
├── hq_audio.py         # 音色克隆 + TTS + audio_assets
├── hq_image.py         # gen_image（泽龙/OpenAI 双引擎）
├── hq_copy.py          # gen_copy / gen_collect / gen_leads
└── hq_video.py         # HeyGen 视频
```

ship 脚本的映射表加上新文件即可（`server/hq_*.py → /home/ubuntu/content-api/`）。拆分是纯搬家，行为不变，可逐域进行、每拆一个域 ship 一次验证。

#### P1-2 死代码：`gen_image` 定义了两次
`server/content_api.py:1121` 和 `:1168` 各定义一个 `gen_image`，前者被后者静默覆盖（Python 后定义生效），~45 行死代码，还会误导后续修改者改错那份。**做法**：删除第一个定义（拆分 P1-1 时顺手完成）。

#### P1-3 跨服务直写别人的数据库
`content_api.py` 通过 `AUTH_DB=/home/ubuntu/auth-service/users.db` **直接打开 auth 服务的 SQLite 扣点数**，同时 auth 服务自己也在写这个库。SQLite 跨进程并发写靠文件锁，高并发下会出现 `database is locked`，且点数逻辑散落两处。
**做法**：auth_server 暴露 `POST /api/auth/points/deduct|refund`（内部端口 127.0.0.1:8095 已天然不对外），content_api 改为 HTTP 调用（它已经这样调 `/api/auth/me` 验 token 了，模式现成）。过渡期至少给两个库开 WAL 模式。

#### P1-4 `server/` 目录职责混乱
`app.py`（8090 获客后端，FastAPI）和 5 个零依赖服务放在一起，还有 `admin.html`、`index.html`、`keywords.json`（8090 的前端/数据）和一份与 `deploy/` 重复的 nginx conf。
**做法**：`server/` 拆为 `server/`（5 个零依赖服务）+ `leadgen/`（app.py + admin.html + index.html + keywords.json + worker/）；nginx conf 只留 `deploy/` 一份（以线上 `/etc/nginx/sites-enabled/huangquechuanmei` 为准回收后入库）。

### 🟡 P1 —— 前端结构

#### P1-5 缓存戳手动维护，已经出过不一致
14 个页面手写 `<script src="cloud-shell.js?v=15">`，本次对账发现 **video.html 还停在 v=14**——用户在 video 页会加载旧版共享外壳，其他页是新版。手动 sed 全站 bump 这种事必然再漏。
**做法**：ship 部署 `site/workbench/*` 时自动把 `cloud-shell.js?v=…` 统一替换为文件内容 hash（10 行 shell 就够）；或者干脆 nginx 对 `.js` 设 `Cache-Control: no-cache` + ETag（体量小，协商缓存足够，一劳永逸）。

#### P1-6 页面级 JS 大量重复
各页内联 script 600~800 行（assets 816、collect 654、video 392……），其中鉴权头拼装、`/api/gen` 提交+轮询、点数显示、错误 toast 等逻辑每页抄一份。已有 `tasks.js`/`auth-guard.js` 但覆盖不全。
**做法**：抽一个 `hq-api.js`（fetch 封装：自动带 Bearer、统一错误处理、submit+poll 任务助手），新页面一律用它；旧页面**不强求一次性重写**，改到哪页迁移哪页。

### 🟢 P2 —— 仓库卫生与保障（有空就做）

| # | 问题 | 做法 |
|---|---|---|
| P2-1 | 业务零测试（tests/ 只有 ci_validate 自测） | 给纯函数补 pytest：`cost_of`、`validate_submit_payload`、`parse_limit`、`_is_spam/_is_high`、auth 的口令哈希/Token TTL。这些不用 mock 外部服务，一下午能写完 |
| P2-2 | CI 只有静态红线检查 | ci.yml 加两步：`python -m py_compile server/*.py`（本次那种"双定义/语法错"能拦住一半）+ `pytest` |
| P2-3 | 文档入口分散（docs/knowledge/design-system/server-overview/archive + 根目录 5 个 md） | 根 README 加一张"从这里开始"导航表；`keywords.md`、散落的 openclaw 文档归入 docs/；不必大动 |
| P2-4 | `run_local.sh` 只覆盖 leadgen（8090），5 个零依赖服务无本地跑法 | 补 `run_local_content.sh`：本地起 auth+content（SQLite 建在 ./local-data/），前端 `python -m http.server` 指向 site/，开发不必直连生产 |
| P2-5 | 服务器上还跑着 Dify、OpenClaw 沙箱等无关负载，内存已用 7.9G/15G + 1.8G swap | 黄雀上量后考虑分机；短期给 5 个 huangque 服务加 systemd `MemoryMax`，防止被邻居 OOM 波及 |

## 三、建议落地顺序

| 批次 | 内容 | 工作量 |
|---|---|---|
| **今天** | 合并 PR #27（基线对齐）→ P0-1 换口令+EnvironmentFile → P0-3 清 .bak（服务器归档 + git 删除 + nginx deny）→ P1-2 删 gen_image 死代码 | ~半天 |
| **本周** | P0-2 漂移哨兵 cron → P1-5 缓存戳自动化 → P0-4 SSH 密钥 → P2-2 CI 加 py_compile | ~半天 |
| **下周起** | P1-1 content_api 按域拆分（逐域、每域独立 ship 验证）→ P1-3 点数收敛到 auth API → P1-4 server/leadgen 目录整理 | 2~3 天，可穿插 |
| **持续** | P1-6 hq-api.js（改到哪页迁哪页）、P2-1 补测试、P2-4 本地开发环境 | 随日常开发 |

**原则**：每一步都是独立小步、可用 `git revert + ship` 一键回滚；拆分类改动（P1-1/P1-3/P1-4）必须在 PR #27 合并、基线干净之后再动。
