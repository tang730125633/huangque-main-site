# 工单 · 运营后台（接口管理 + 用户管理 + 充值审批）

> 供其他 agent 独立执行。先读《工单-其他agent实施》§0 +《开发手册》+《任务看板》领取流程。
> **大工单，分 3 阶段交付**（可分 3 个 PR）。冲突组见每阶段标注。
> 需求：kongli —— 现在改用户点数/查平台状态都得手动上服务器改库，要一个可视化运营后台。

## 背景现状（已调研）
- **没有真正的运营后台**。`/api-admin` 只是**静态"API 基建总表"**（团队密码守护，密钥真值不在页面）；`/admin`（app.py）是**获客账号池**管理，与平台用户无关、且弱口令 `admin123`。
- `auth` 的 users 表有 `role`（member/admin）**但没有任何后台用到它**。
- **充值纯线下**：`recharge.html` 只有"立即购买/联系销售"，无后端、无订单表。
- **点数无流水**：只有 `users.points` 余额；加减点需新建审计流水。
- 健康端点齐全：`/api/auth/health`(8095) `/api/gen/health`(8096) `/api/gen/banana/health`(8101) `/api/gen/leadgen/health`(8100)。
- 调用统计数据源：`content_jobs.db` 的 jobs 表（kind/status/created_at 可聚合）。

## 架构（三方共识，先定）
- **新建独立后台服务** `server/admin_api.py`（新端口，建议 **8099**，systemd 新 unit `huangque-admin`，User=ubuntu）。只读 users.db / jobs.db + 探活各服务；写操作（加点/审批）走 **auth 内部原子接口**或带审计。
- **新建后台前端** `site/admin/index.html`（替代/升级现有静态 `/api-admin`；nginx 把 `/admin-console/` 或复用 `/api-admin` 指向它）。
- **鉴权**：用现有 `role=admin`——管理员用平台账号登录，后台每个接口都校验 `verify(token)` 且 `role=='admin'`，非 admin 一律 403。**禁止再引入 admin123 式共享弱口令。**
- **安全铁律**：① 任何接口**绝不返回密钥真值**（只返回"是否已配置/来自哪个 env"）；② 所有写操作（加减点、审批、渠道开关）**写审计日志**（谁、对谁、改了啥、何时、原因）；③ 全部 admin 接口强制 role=admin 校验。

## 阶段一 · 接口管理（先做，MVP）
> **冲突组：新建 `server/admin_api.py` + `site/admin/index.html`（均新文件，独立）** —— 抢 `lock/admin`。不碰现有后端/前端。

后台服务骨架 + 管理员登录（role=admin 校验）+ 下列「接口管理」四块：
1. **渠道状态 + 健康监控**：实时探各服务健康端点（auth/content/imggen/leadgen + dl），显示 在线/离线、端口、服务文件、响应耗时。外部 API（HeyGen/RunningHub/OpenAI/tikhub/COS）显示连通性（有 selftest 就用，如 content health 已返回 has_openai/has_tikhub）。
2. **密钥状态（不显真值）**：每个渠道的 key **是否已配置**、来自哪个 env 文件（如 `runninghub.env`/`content.env`），**绝不显示真值**。方便排查"哪个 key 没配/失效"。
3. **渠道开关 / 配置**：管理员可启用/禁用某渠道、编辑**非密钥**配置（如成本值、限流、默认参数）。落到一个 admin 配置存储（新表/新 json），改动即时生效（服务读该配置）。**注意**：改成本这类要和现有 COST 打通，避免两套真相。
4. **接口调用统计**：从 jobs 表聚合各 kind（image/video/tryon/audio/collect…）的调用量、成功/失败率、近 N 天趋势；标出异常高失败项（如 HeyGen 动作模仿、tikhub 400）。

**验收**：管理员（role=admin）能登录后台看到各服务在线状态、密钥配置情况（无真值）、调用统计；能开关渠道且生效；非 admin 访问全部 403。

## 阶段二 · 用户管理
> **冲突组：`server/admin_api.py`（lock/admin）+ `server/auth_server.py`（lock/D）+ `site/admin/`** —— 抢 `lock/admin` 和 `lock/D`。

1. **用户列表**：展示所有账号 username / display_name / points / role / must_change / created_at；支持搜索、按点数/时间排序。
2. **点数管理**：给指定用户**加/减点**（替代现在手动改库）。
   - auth 加 admin 专用**原子调点接口**（如 `POST /api/auth/admin/points/adjust`，body `{username, delta, reason}`，`BEGIN IMMEDIATE`），带 `role=admin` 校验 + 内部 token。
   - **新建点数审计流水表**（who_admin, username, delta, before, after, reason, at），每次调点写一条。后台可查流水。
3. （可选）**改角色 / 重置 must_change / 封禁**：谨慎，带二次确认 + 审计。

**验收**：admin 能查用户列表、给用户加减点且**原子生效 + 有流水**；普通用户无法调用；点数变更与 `/api/auth/me` 一致。

## 阶段三 · 充值审批
> **冲突组：`server/admin_api.py`（lock/admin）+ `site/workbench/recharge.html`（lock/E-recharge）+ auth（lock/D）** —— 抢对应锁。

1. **用户侧**（recharge.html）：把"立即购买"改成**提交充值申请**（选套餐/填金额+备注 → 存"充值订单"表，状态 pending）；提示"等管理员确认到账"。
2. **订单表**（新建）：order_id, username, amount(钱), points(应到点数), status(pending/approved/rejected), note, created_at, reviewed_by, reviewed_at。
3. **管理员侧**（后台）：待审充值列表 → **确认到账**（approve → 调阶段二的原子加点接口给用户加点、订单转 approved、写审计）或**驳回**（reject + 原因）。

**验收**：用户能发起充值申请；管理员后台能看到待审、点确认后**用户点数自动到账（原子+流水）**、订单状态更新；驳回可用。

## 全局边界与注意
- **只新增**：admin 服务 + admin 前端 + auth 的 admin 调点接口 + 订单/审计表 + recharge 提交。**不动**生成主流程、不动普通用户鉴权主流程。
- **密钥安全**：后台任何地方不落、不显密钥真值；新服务若需读 users.db/jobs.db 用只读连接。
- **审计**：所有写操作留痕。
- **部署**：新服务需 systemd unit `huangque-admin`（新端口 8099）+ nginx 反代一个后台路径；密钥/内部 token 走 env 不进 git。审核方部署时配。
- 保持 `DESIGN.md` 视觉规范（后台可用更朴素的管理风，但配色/字体沿用）。

## 交付方式
- **分 3 个 PR**（阶段一 / 二 / 三），每个 PR 独立可上线、独立验收。先交阶段一（接口管理 MVP）。
- 每阶段：`py_compile` / 现有 unittest 全过、health 200、非 admin 403 用例覆盖。

## 部署前置（审核方/ops）
- 新 systemd unit `huangque-admin`（8099，EnvironmentFile 复用或新增，含内部 token）。
- nginx 加后台路径反代到 8099。
- 至少 1 个 `role=admin` 账号（用 `auth_server.py create <user> <pass> <pts> admin` 或改库）。
