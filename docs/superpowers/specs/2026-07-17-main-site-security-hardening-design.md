# 主站第一批安全加固设计

日期：2026-07-17
实施仓库：`LU-003/huangque-test-server`
未来合并目标：`tang730125633/huangque-main-site`
开发与验证环境：`8.138.143.64`
生产环境：`129.204.166.13`

## 1. 目标

在不改变现有业务价格、不迁移数据库、不重写认证系统的前提下，优先降低以下高风险：

1. 公网能够到达只应由本机服务调用的扣点、退款和内部管理接口。
2. Cookie 登录下的状态变更接口缺少统一 CSRF 与请求来源验证。
3. 管理后台直接暴露公网，缺少网络入口限制和敏感操作二次确认。
4. Nginx、认证服务和管理员服务缺少针对上述边界的自动化回归测试。

本批次的目标是“先封入口、再补请求校验、最后限制后台”，不在同一批次重构点数账本、支付流程、密码算法或 Session 存储。

## 3. 推荐架构

### 3.1 公网与内部接口分离

Nginx 在通用 `/api/auth/` 代理规则之前增加精确拒绝规则。以下路径从公网统一返回 404：

- `/api/auth/points/deduct`
- `/api/auth/points/refund`
- `/api/auth/admin/points/adjust`
- `/api/auth/admin/points/audit`
- `/api/auth/admin/users`
- `/api/auth/admin/recharge/review`
- `/api/auth/admin/recharge/orders`

内容服务、图片服务、获客服务和管理员服务继续直接访问 `http://127.0.0.1:8095`，不经过公网 Nginx。

公网 `/api/auth/` 代理必须清空客户端提供的 `X-HQ-Internal-Token`，避免客户端把该头转发到认证服务。内部调用仍由各 systemd 服务从受保护环境文件读取令牌并直接连接 8095。

### 3.2 状态变更请求保护

认证服务新增统一的浏览器状态变更校验函数，作用于使用 Cookie 身份的 `POST`、`PUT`、`PATCH` 和 `DELETE` 请求：

1. 只接受 `Content-Type: application/json`，支付平台回调和文件上传端点按明确白名单例外处理。
2. 检查 `Origin`；缺失时回退检查 `Referer`。
3. 来源必须精确匹配配置的主站 Origin，不使用后缀或模糊匹配。
4. 浏览器请求要求 `X-CSRF-Token`，其值与当前 Session 绑定。
5. Bearer Token 的服务端或小程序调用不自动继承浏览器 Cookie 规则，但仍执行认证、权限和内容类型校验。
6. 微信支付回调使用现有平台签名验证，不要求浏览器 CSRF Token。

CSRF Token 由服务端生成并与 Session 关联。前端通过登录结果或单独的只读端点取得 Token，后续状态变更请求放入自定义请求头。Token 不写入 URL、不写入日志。

### 3.3 管理后台入口

管理后台采用两层保护：

1. Nginx 网络层：默认仅允许配置的管理 IP 段；测试环境允许测试人员当前出口 IP。若无法固定 IP，则改用 VPN/零信任网络，不使用长期开放的公网入口。
2. 应用层：继续保留 Session + `role=admin` + 内部令牌校验。

管理员调点和充值审批新增敏感操作确认字段：

- 强制填写原因；
- 原因长度 4～120 字符；
- 请求必须携带 CSRF Token；
- 审计记录保留管理员、目标用户、前后余额、原因和请求 ID；
- 单次调点超过配置阈值时拒绝，后续批次再设计双人审批。

### 3.4 Nginx 安全响应头

在不破坏现有页面的前提下补充：

- `Strict-Transport-Security`
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy`
- `Permissions-Policy`
- `frame-ancestors 'self'`（通过 CSP）

第一批不直接移除 CSP 的 `unsafe-inline`，因为现有页面包含大量内联脚本和样式；先记录为第二批任务，避免一次性造成全站页面失效。

## 4. 请求数据流

### 4.1 普通用户生成任务

1. 浏览器提交生成参数和 CSRF Token。
2. 内容服务从 Session 取得用户名，不采用客户端提交的用户名。
3. 内容服务按服务端价格表计算费用。
4. 内容服务通过 127.0.0.1 调用认证服务扣点。
5. 认证服务验证内部令牌并原子扣点。
6. 返回服务端余额；前端只负责显示。

### 4.2 管理员调点

1. 管理员从受限网络访问后台。
2. 浏览器携带管理员 Session 和 CSRF Token调用 `/api/admin/points/adjust`。
3. 管理服务检查管理员角色、原因和调整范围。
4. 管理服务通过 127.0.0.1 携带内部令牌调用认证服务。
5. 认证服务再次检查管理员 Session 与角色，完成事务和审计。

## 5. 错误处理

- 公网访问内部接口：返回 404，不暴露接口是否存在。
- CSRF Token 缺失或错误：返回 403，记录安全事件，不返回 Token 细节。
- Origin/Referer 不匹配：返回 403，记录来源、路径、请求 ID和客户端 IP。
- 非 JSON 状态变更请求：返回 415。
- 管理后台来源 IP 不允许：Nginx 返回 403，不转发应用服务。
- 管理员原因缺失、调整为 0、超过阈值：返回 400，不写余额和审计流水。
- 安全校验异常：默认拒绝，不采用“校验失败则放行”。

## 6. 测试设计

### 6.1 单元测试

- 普通用户不能调用管理员调点、用户列表和审计接口。
- 公网 Nginx 配置包含内部端点精确拒绝规则。
- 客户端提供的 `X-HQ-Internal-Token` 不会被代理到认证服务。
- Cookie 状态变更请求缺少 CSRF Token 时返回 403。
- Origin 不匹配、伪造子域名和 `null` Origin 均被拒绝。
- 合法 Origin + 合法 Token 可以完成原业务操作。
- Bearer Token、小程序和微信支付回调的明确例外仍可工作。
- 管理员调点必须有合格原因，并保留审计信息。

### 6.2 集成测试

- 注册、登录、退出、修改密码、个人资料、充值、生成任务完整回归。
- 图片、视频、文案、获客等服务仍可从本机正常扣点与退款。
- 外网直接请求扣点/退款接口得到 404。
- 普通用户修改请求里的用户名、角色、点数和价格均不能影响真实余额。
- 同时执行并发扣点，余额不会小于零。
- 管理后台从允许 IP 可访问，从非允许 IP 被拒绝。

### 6.3 安全测试

- 使用 OWASP ZAP 对测试环境执行被动扫描和受控主动扫描。
- 对所有带用户 ID、任务 ID、画布 ID 的接口执行横向越权测试。
- 对登录、注册、管理员接口执行限流测试。
- 检查响应头、Cookie 属性、CORS 和 CSP。
- 检查日志不包含 Session、CSRF Token、内部令牌和 API 密钥。

## 7. 测试服务器实施方式

1. 在 `LU-003/huangque-test-server` 最新 `main` 上创建独立分支 `codex/main-site-security-hardening`。
2. 所有安全代码只在该分支修改；不从主站运行目录直接改文件，也不向主站仓库写入任何提交。
3. 测试环境使用独立数据库、内部令牌、管理员账号和 IP 白名单，不复制生产用户数据或生产支付密钥。
4. 部署前备份测试数据库、Nginx 和 systemd 配置。
5. 完成单元测试和完整测试后部署到 `8.138.143.64`。
6. 完成攻击验证后观察 24～48 小时，确认登录、点数、支付和生成任务无回归。

## 8. 合并主站方式

由于 `LU-003/huangque-test-server` 不是主站仓库的标准 fork，不能把测试仓库 `main` 直接合并到主站。当前阶段只在用户仓库开发和部署。未来确认需要上线主站时，安全改动必须保持为少量、独立、可 cherry-pick 的提交：

1. Nginx 公网边界与安全响应头；
2. CSRF/Origin 服务端校验与前端请求头；
3. 管理员入口和调点保护；
4. 安全测试与部署文档。

未来合并前先读取主站最新 `main`，在独立适配 worktree 中逐个 cherry-pick 安全提交并解决兼容差异。若具备主站仓库分支权限，则将适配后的提交推送到主站安全分支并创建 PR；否则导出 `git format-patch`，由主站维护者在最新 `main` 上 cherry-pick。生产服务器禁止直接提交或解决冲突。

## 9. 发布与回滚

发布前：

- 主站数据库、Nginx、systemd 和环境文件完成备份；
- 记录当前生产 SHA；
- `nginx -t`、完整测试和安全测试通过；
- 确认管理员允许 IP，避免上线后锁死后台。

发布顺序：

1. 部署认证服务与管理员服务代码；
2. 部署前端 CSRF 请求头支持；
3. 最后启用 Nginx 拒绝规则、IP 白名单和安全响应头；
4. 重新加载 Nginx，按需重启认证和管理员服务；
5. 执行登录、点数、支付和生成任务冒烟测试。

回滚顺序：

1. 恢复上一版 Nginx 配置并 reload；
2. 切回上一已验证代码 SHA；
3. 恢复服务并验证；
4. 本批次不改变数据库结构，因此正常情况下不需要恢复数据库。
