# xAI 视频任务可恢复轮询设计

## 背景

测试环境中的 xAI 视频任务已经成功提交并获得 `request_id`，但轮询期间一次 HTTP 503 被当作永久失败处理。网站立即把任务标记为失败并退点，而 xAI 上游仍保持 `pending`。当前启动流程还会把服务重启遗留的全部 `running` 任务直接判失败，因此已付费创建的上游任务无法续查。

本设计仅调整 xAI 官方视频通道。其他视频供应商、图片生成、口播和点数定价不在范围内。

## 目标

- xAI 付费创建请求最多发送一次，不因轮询失败或服务重启重复提交。
- 收到 `request_id` 后立即持久化，后续轮询和下载始终复用该 ID。
- 对网络异常及 HTTP 408、429、500、502、503、504 自动退避重试。
- 服务重启后恢复已有 xAI 任务，而不是立即失败退点。
- 仅在明确终态失败、不可恢复错误或总时限耗尽时失败并幂等退点。
- 补偿性恢复当前任务 7，不重新扣点、不发送第二次创建请求。

## 非目标

- 不改变视频价格、并发上限或 xAI 模型参数。
- 不为 xAI 创建请求添加盲目重试。
- 不改造所有第三方供应商的任务协议。
- 不保证在“上游已接受 POST、进程却在收到响应前崩溃”这一无法确认送达的窗口自动重试；在没有上游幂等键的前提下，宁可退点并人工核对，也不能重复计费。

## 状态与数据

`jobs` 继续保存面向用户的任务状态和点数结算；`audio_assets.db` 中的 `video_assets` 保存供应商状态。收到创建响应后，必须在第一次轮询之前调用 `update_video_asset_phase`，写入：

- `provider_video_id=request_id`
- `phase=xai_pending`
- `status=running`
- `model`

恢复任务的判定条件为：

- `jobs.status = running`
- `jobs.kind = xiaole_video`
- `video_assets.provider_video_id` 非空
- `video_assets.phase` 以 `xai_` 开头，或处于已拿到上游结果后的 `downloading`

## 提交与轮询流程

1. `generate()` 或 `edit()` 选择一次代理并发送一次创建 POST。
2. 创建成功后立即持久化 `request_id`，再进入轮询。
3. 新增 `resume(request_id, ...)`，直接进入相同轮询流程，绝不发送创建 POST。
4. 轮询成功返回 `pending` 时刷新资产阶段和任务心跳。
5. 网络异常或 HTTP 408、429、500、502、503、504 使用 5、10、20、30 秒的封顶退避，并继续刷新心跳。
6. 所有重试共用现有 `XAI_VIDEO_TIMEOUT` 总时限，不因单次成功或失败重置截止时间。
7. `done` 后继续现有下载、封面提取、入库和任务完成流程。

## 错误分类与点数

可恢复错误：网络异常、408、429、500、502、503、504。这些错误不得把 `jobs` 或 `video_assets` 写成失败，也不得退点。

不可恢复错误：参数错误、鉴权失败、余额不足，以及 xAI 明确返回 `failed` 或 `expired`。这些错误沿用当前 CAS 终态和 `_refund_once`，确保最多退点一次。

总时限耗尽后写入包含最后一次临时错误的明确错误信息，再进入失败和幂等退点流程。

## 服务重启恢复

`reclaim_orphaned_running()` 分流处理：

- 有持久化 xAI `request_id` 的任务不判失败，改回 `pending` 并由现有队列恢复。
- 其他无法证明已经提交到上游的孤儿任务维持当前“失败并退点”行为。

worker 处理恢复任务时，xAI 调用点先查询 `video_assets`。存在可恢复 ID 时调用 `resume()`；不存在时才允许调用 `generate()` 或 `edit()`。这样现有队列、并发闸、心跳和 CAS 终态机制均可复用。

## 当前任务补偿

任务 7 已经退点，供应商 ID 为 `6680de26-4069-91bc-b8ec-01b9667a66e9`。部署新逻辑后执行一次专用恢复：

- 查询原 ID，不创建新任务。
- 若完成，则下载并写回任务与视频资产结果。
- 保持 `refunded=1`，不重新扣除 300 点，作为本次系统误判的补偿。
- 若上游明确失败或过期，只保留原失败和退点状态。

## 并发与安全

- 创建 POST 不做 5xx 或超时重试，避免重复计费。
- 恢复任务通过现有 `jobs` CAS 认领，防止多个 worker 同时处理。
- `request_id`、模型和阶段可以记录；API Key、COS 密钥和带签名媒体 URL 不写日志。
- 下载是幂等 GET，可沿用现有多通道重试。

## 测试

新增单元测试覆盖：

1. `pending -> 503 -> pending -> done` 最终成功。
2. 轮询出现多个临时错误时，创建 POST 仍只调用一次。
3. 401、402、403、普通 400 立即失败。
4. xAI 返回 `failed` 或 `expired` 时进入终态失败。
5. 总时限耗尽后失败，错误包含最后一次临时异常。
6. POST 成功后在第一次 GET 前持久化 `request_id`。
7. 重启回收把可恢复 xAI 任务改回队列，不退点。
8. 恢复 worker 调用 `resume()`，不会调用创建 POST。
9. 非 xAI 孤儿任务仍按原逻辑失败并幂等退点。

## 验收标准

- 相关单元测试全部通过，现有内容服务测试无回归。
- 内容服务健康接口返回 200，systemd 服务保持 `active`。
- 用模拟响应证明 503 后继续轮询且没有第二次 POST。
- 重启测试证明已有 `request_id` 的任务能够续查。
- 当前任务 7 只查询原 ID，并按上游真实终态恢复或保留失败。
- 验证过程不创建新的付费 xAI 视频任务。
