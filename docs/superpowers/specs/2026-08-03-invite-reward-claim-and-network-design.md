# 邀请奖励待升级领取与会员关系网络设计

## 1. 目标

在保持现有会员等级、开通方式、邀请绑定关系和奖励矩阵不变的前提下，完成两项改造：

1. 当直接邀请人不是会员或会员等级不足时，给予 7 天升级领取期；到期后把奖励转给邀请链中最近的合格上级。
2. 将小程序邀请中心的“奖励记录”改为“我的下线”，支持会员按层级查看邀请关系，并接入正在开发的用户名片系统。

本次规则只处理上线后新产生的会员开通、升级和退款事件。历史邀请关系可用于关系浏览，但不重算、不补发、不迁移历史奖励。

## 2. 不在本次范围内

- 不修改会员等级、会员有效期、线上或线下开通方式。
- 不修改现有邀请绑定、防刷和邀请码规则。
- 不修改现有奖励矩阵及既有特殊限制。
- 不开发名片编辑、发布或媒体管理功能，只消费名片系统提供的查询能力。
- 不追溯历史会员订单，不为历史事件创建待领取记录。
- 不把邀请奖励并入普通消费点数；继续使用独立邀请奖励账本。

## 3. 术语

- **直接邀请人**：`user_invites` 中与被邀请人直接绑定的上一级用户。
- **目标等级**：被邀请人本次有效会员事件达到的等级，也是直接邀请人领取奖励所需达到的最低等级。
- **合格领取人**：账号有效、会员未过期，且会员等级不低于目标等级的用户。
- **待升级奖励**：直接邀请人当前不合格，但可在 7 天内通过升级获得的奖励资格。
- **上级转移**：待升级奖励到期后，从直接邀请人的上级开始逐级寻找合格领取人。

会员等级顺序为：非会员 `<` 体验官 `<` 合伙人 `<` 发起人。

## 4. 奖励业务规则

### 4.1 直接结算

被邀请人的会员开通或升级事件生效后：

1. 查询有效的直接邀请关系。
2. 如果直接邀请人是合格领取人，立即按该邀请人当前会员等级对应的现有奖励矩阵结算。
3. 如果直接邀请人是非会员、会员已过期或等级低于目标等级，创建 7 天待升级奖励。

奖励金额由最终领取人的有效会员等级和被邀请人的目标等级共同决定，继续使用现有矩阵：

| 最终领取人等级 | 被邀请人成为体验官 | 被邀请人成为合伙人 | 被邀请人成为发起人 |
| --- | ---: | ---: | ---: |
| 体验官 | 200 | 不符合 | 不符合 |
| 合伙人 | 240 | 1500 | 不符合 |
| 发起人 | 280 | 2500 | 15000 |

“不符合”不代表奖励立即消失，而是直接邀请人进入待升级领取流程。

### 4.2 七天升级领取

- 领取期从会员事件确认生效的服务器时间开始，持续 `7 * 24` 小时。
- 到期时间以 UTC 时间戳存储，界面按服务器时间计算剩余时间。
- 直接邀请人在期限内达到目标等级后，系统自动结算全部仍有效且已满足条件的待升级奖励。
- 不设置手动领取按钮。
- 最终金额按结算时领取人的实际有效等级重新计算。例如待领取目标为体验官，用户直接升级为合伙人时，按合伙人邀请体验官的标准结算。
- 列表中的待领取额度按达到目标最低等级后的可领取金额展示；最终到账金额可能因实际升级到更高等级而增加。

### 4.3 到期向上转移

到期时直接邀请人仍不合格，系统从其直接上级开始逐级查找：

1. 跳过非会员、会员已过期、账号无效和等级不足的用户。
2. 找到第一个合格领取人后停止查找。
3. 按该领取人的当前有效会员等级和目标等级计算奖励并自动结算。
4. 记录转移层级、原直接邀请人、最终领取人和结算金额。
5. 如果整条有效邀请链都没有合格领取人，标记为“无合格领取人”，不发放奖励。

关系遍历必须设置最大深度并检测循环。当前数据模型每个用户只有一个直接邀请人，但实现不能依赖数据库永远无异常数据。

### 4.4 退款、撤销和失效

- 被邀请人的会员订单在待领取期间退款，或会员资格被撤销、失效，对应待升级奖励立即作废。
- 作废后的奖励不再向上转移。
- 已经结算到账的奖励不自动倒扣，进入运营后台人工处理范围，避免产生负奖励余额或误扣其他奖励。

### 4.5 幂等与并发

- 每个有效会员事件只允许对应一条奖励资格记录。
- 使用 `membership_upgrade_records.id` 作为唯一业务键；有支付订单号时同时记录来源订单号。
- 会员升级回调、支付回调、定时到期任务和人工升级可能并发，结算时必须在同一数据库事务内锁定资格记录并做状态条件更新。
- 只有从待处理状态成功变更为终态的执行者可以写入奖励账本。
- 重复回调只返回已有结果，不重复发奖或重复弹窗。

## 5. 数据模型

### 5.1 新增 `invite_reward_claims`

待领取生命周期与已经确认的奖励账本分开存储。结算成功后继续写入现有 `invite_reward_point_records`。

建议字段：

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `upgrade_record_id` | 唯一会员事件 ID |
| `source_order_id` | 可空的来源订单号 |
| `invite_relation_id` | 直接邀请关系 ID |
| `direct_inviter_user_id` | 原直接邀请人 |
| `invitee_user_id` | 被邀请人 |
| `target_level` | 领取要求的最低会员等级 |
| `event_type` | 开通、升级或现有系统支持的会员事件类型 |
| `status` | 资格状态 |
| `created_at` | 创建时间 |
| `expires_at` | 七天到期时间 |
| `recipient_user_id` | 最终领取人，可空 |
| `recipient_level_snapshot` | 结算时领取人等级 |
| `reward_points` | 最终结算额度，待处理时为最低等级预计额度 |
| `transfer_depth` | 向上转移层级，直接领取为 0 |
| `settled_at` | 到账时间 |
| `voided_at` | 作废时间 |
| `reason` | 终态原因或审计说明 |
| `updated_at` | 更新时间 |

状态定义：

- `pending_upgrade`：等待直接邀请人升级。
- `credited`：直接邀请人已领取并到账。
- `transferred`：已转给最近的合格上级并到账。
- `voided`：退款、撤销或资格失效导致作废。
- `no_recipient`：到期后没有合格上级。

### 5.2 现有表的使用

- `user_invites`：继续作为唯一邀请关系来源。
- `membership_upgrade_records`：继续作为会员事件来源和幂等依据。
- `invite_reward_point_records`：只记录已经确认到账的奖励；新增对 `claim_id` 和最终领取来源的可追踪字段时采用兼容性迁移。
- 运营审计记录必须保留直接邀请人、最终领取人、转移深度、状态变化前后值和操作来源。

## 6. 结算组件

将规则集中在后端邀请领域模块，避免支付、后台升级和小程序接口各自实现一套逻辑。

### 6.1 `create_or_settle_claim`

输入会员事件，在同一事务中校验邀请关系、现有特殊限制和领取资格。直接邀请人合格时立即结算，否则创建待升级记录。

### 6.2 `settle_pending_for_user`

会员充值成功或管理员升级成功后调用。查找该用户全部未到期的待升级记录，逐条校验后自动到账，并返回本次解锁笔数和到账总额供前端展示。

### 6.3 `expire_pending_claims`

定时处理已到期记录。逐级寻找最近的合格上级，并把记录原子地变更为 `transferred` 或 `no_recipient`。

### 6.4 `void_claims_for_membership_event`

会员退款、资格撤销或相关订单失效时调用。只允许把尚未到账的记录变更为 `voided`。

## 7. “我的下线”与关系浏览

### 7.1 页面结构

- 邀请中心把“奖励记录”改为“我的下线”。
- 首页只显示当前用户的一级直接下线，每页 20 条。
- 每条用户信息展示用户名、当前有效会员等级、奖励展示字段和“名片”按钮。
- 点击用户信息区域进入该用户的关系页。
- 关系页展示该用户的直接上线和一级下线，可继续点击上线或下线逐层浏览。
- 每次只加载一个用户的一层相邻关系，不一次展开整棵邀请树。
- 页面维护返回路径，用户可以按原访问顺序返回。

### 7.2 浏览权限

- 非会员只能查看自己的一级下线，不能点击进入其他用户的关系页。
- 有效会员可以从自己的关系页开始，沿有效邀请关系逐层向上或向下浏览同一邀请网络。
- 会员失效后立即失去浏览其他用户关系的权限。
- 查看其他用户时只返回用户名、会员等级和上下线关系。
- 不返回手机号、邀请码、账户余额、普通点数余额或其他用户的奖励明细。
- 服务端不能只依赖前端隐藏按钮。每次请求都必须重新校验登录用户的会员状态和目标节点的访问路径。
- 目标用户使用不可枚举的节点标识。相邻节点响应应提供与当前登录用户绑定、短时有效的访问凭证，防止通过猜测用户 ID 横向读取关系网络。

### 7.3 名片按钮

- 每条用户信息右侧始终显示“名片”按钮，按钮点击与用户信息点击相互独立。
- 已发布且可查看名片时，进入同事开发的名片详情页。
- 未创建、未发布或不可查看时，提示“该用户暂未创建名片”，不跳转。
- 名片接口异常时使用同一提示，不阻塞下线列表和关系浏览。
- 本功能只依赖名片系统返回稳定的名片状态和公开标识，不重复实现名片业务。

## 8. 奖励展示规则

### 8.1 非会员与体验官

- 返回并展示真实累计奖励额度。
- 下线列表可展示该下线产生的奖励额度、状态和到期倒计时。
- 待升级记录展示目标等级、最低预计奖励额度和服务器到期时间。
- 终态展示“已到账”“已转移”“已作废”或“无合格领取人”。

### 8.2 合伙人与发起人

- 小程序和网页的累计奖励额度固定返回 `0`。
- 下线列表中的奖励额度固定返回 `0`。
- 不返回真实奖励金额、奖励记录或其他用户奖励详情。
- 用户名、会员等级、上下线关系和名片按钮正常展示。
- 合伙人因邀请发起人而等级不足时，仍可收到升级提醒和剩余期限，但不展示具体奖励金额。
- 真实奖励和结算状态继续在后端保存，仅运营后台可查。

后端必须按当前登录用户等级生成脱敏响应，不能把真实金额发给前端后再由前端隐藏。

## 9. 升级提醒与到账反馈

### 9.1 待升级提醒

- 待升级奖励首次产生时提醒一次。
- 此后每天首次进入小程序提醒一次，直到到账、转移、作废或无合格领取人。
- 体验官开通可引导到线上会员购买入口。
- 合伙人和发起人升级继续提示联系管理员。
- 提醒记录由后端按用户、资格记录和上海自然日控制，避免不同设备重复弹窗。

### 9.2 升级后奖励反馈

会员支付或后台升级完成后，前端等待后端返回本次待奖励结算结果：

- 标题：“升级成功，邀请奖励已解锁”。
- 非会员或体验官升级后显示本次到账点数。
- 合伙人、发起人不显示具体点数，只显示“邀请权益已自动发放”。
- 一次升级解锁多笔时，非会员或体验官显示笔数和总到账点数。
- 提供“查看我的下线”和“知道了”两个操作。
- 支付已成功但奖励事务尚未确认时显示“奖励结算中”，后端确认后通过下一次状态查询补弹最终结果。
- 到账反馈必须由唯一结算结果驱动，前端不得根据支付成功自行推断已发奖。

## 10. API 设计

具体路径遵循现有 `/api/auth/invite/*` 与 `/api/auth/network/*` 风格，以下为响应职责而非强制命名。

### 10.1 下线分页接口

返回：

- 当前查看节点的最小公开信息。
- 直接上线的最小公开信息。
- 一级下线列表与分页游标。
- 每个用户的会员等级、名片状态、不可枚举节点标识和访问凭证。
- 按查看者等级过滤后的奖励展示字段。

默认和小程序固定页大小为 20，服务端设置合理上限。

### 10.2 待升级摘要接口

返回当前用户可见的待升级笔数、要求等级、到期时间、提醒状态和脱敏后的额度。服务器同时返回 `server_time`，小程序只负责渲染倒计时。

### 10.3 到账反馈接口

按结算批次返回尚未确认展示的到账结果。前端展示成功反馈后提交已读状态，保证换设备不会持续重复弹窗。

### 10.4 兼容性

- 所有新增响应字段采用向后兼容方式添加。
- 旧版小程序调用原奖励接口时仍得到原有结构。
- 合伙人和发起人的现有隐藏规则继续生效。
- 名片系统尚未完成或接口不可用时，不影响邀请中心其他功能。

## 11. 运营后台与审计

运营后台可以查询真实数据，包括：

- 直接邀请人、被邀请人和最终领取人。
- 目标等级、最终领取人等级、奖励金额和转移层级。
- 创建、到期、结算、转移和作废时间。
- 会员事件和来源订单。
- 当前状态和原因。

本次不要求新增人工发奖操作。现有人工奖励处理能力如需接入，必须继续经过审计并保证幂等。

## 12. 失败处理

- 会员事件已成功但奖励处理暂时失败：会员结果不回滚，记录可重试的结算任务，并向前端返回“奖励结算中”。
- 定时任务失败：保留 `pending_upgrade`，下一轮继续处理，不提前变成终态。
- 名片查询失败：降级为“暂未创建名片”。
- 关系数据出现循环：停止遍历、记录告警，不发放可能重复的转移奖励。
- 领取人结算瞬间会员过期或账号失效：事务内重新校验并继续寻找下一位合格上级。
- 数据库迁移失败：停止服务发布，不允许在部分新表或索引缺失的状态下运行。

## 13. 测试与验收

### 13.1 奖励规则

- 覆盖非会员、体验官、合伙人、发起人的全部邀请等级组合。
- 验证直接到账、等级不足待升级、七天内升级、多笔同时解锁。
- 验证最终金额按实际领取人等级计算。
- 验证到期跳过非会员、失效会员、账号异常用户和等级不足用户。
- 验证整条链无合格领取人时不发奖。
- 验证退款或资格撤销使待领取奖励作废且不转移。
- 验证重复支付回调、重复后台升级和重复定时任务不会重复发奖。

### 13.2 权限与隐私

- 非会员只能查看自己的一级下线。
- 有效会员可以逐层向上、向下访问同一邀请网络。
- 会员过期后访问立即被拒绝。
- 伪造、过期或属于其他登录用户的节点访问凭证被拒绝。
- 响应中不包含手机号、邀请码、余额和未授权奖励数据。
- 合伙人、发起人在网页和小程序看到的奖励额度始终为 `0`。

### 13.3 小程序交互

- 一级下线分页每页 20 条，空列表、末页和重复加载行为正确。
- 用户信息点击与名片按钮点击互不冲突。
- 已创建名片正常跳转，未创建和接口异常显示指定提示。
- 倒计时使用服务器时间，切后台和重新进入后不会漂移。
- 待升级提醒按首次产生和每天首次进入规则展示。
- 升级后展示正确的到账、合并到账或结算中反馈。
- 合伙人、发起人的反馈不泄露真实奖励额度。

### 13.4 上线验证

- 数据库迁移只新增结构，不改写历史邀请和历史奖励。
- 后端先上线并通过旧版小程序兼容性验证。
- 小程序审核发布前使用受控账号验证四种会员等级、真实分页和名片降级路径。
- 上线后核对奖励资格表、原奖励账本、用户可见响应和运营后台审计四者一致。

## 14. 发布顺序与回滚

1. 备份数据库并执行兼容性迁移。
2. 上线支持新旧接口的后端。
3. 运行只读检查与受控测试，确认历史奖励未变化。
4. 提交并发布小程序页面。
5. 开启到期处理任务并监控异常。

回滚小程序不影响后端资格记录。回滚后端时保留新增表和数据，不删除已经创建的待领取记录；修复后重新运行幂等结算任务。
