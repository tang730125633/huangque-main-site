## 问题（Issue #162）
生成进度条"感觉怪怪的"，跨生成类型体验不一致：
- **视频（动作模仿/换装）**：进度条大跳（8→34→52→84%）、长阶段长时间卡在固定百分比（如 64% "数字人生成中(较久)"、84% "视频渲染中(较久)"）、ETA 是写死静态字符串不倒计时、5 个步骤点更新不连贯、bar 很细(5px)。
- **采集**：只有"爬取中(XXs)"纯文字计时，无可视化进度条/阶段。
- **其它（图片/脚本/配音）**：反馈更弱，多为按钮禁用+完成刷新。

## 根因（issue 已分析）
进度是**纯客户端阶段模拟值**，不是真实时间/provider 百分比；各 phase 耗时极不均匀；心跳只为防 reaper 不为体验；缺 indeterminate 态/时间插值/统一组件。

## 目标：让进度"顺滑、可信、一致"（前端优化，不苛求真实百分比）
### 视频（`video.html` 的 `phaseInfo`/`progressMarkup`/`updateJobProgress`）
1. **阶段内时间插值**：在两个 phase 检查点之间，按**已用时间平滑推进**进度条（而不是停在固定值），接近该阶段预期上限时放缓、不冲顶（留给下阶段）。
2. **长阶段用 indeterminate 动画**：对"较久"的阶段（数字人生成/视频渲染/RunningHub 等待）叠加**流动/脉冲动画**，表示"仍在进行"而非卡死。
3. **ETA 动态化**：把写死的静态 ETA 改成**随已用时间递减的估算**（或至少显示"已用 Xs"而非假倒计时）；估不准时用"预计较久，请耐心等待"这类诚实文案。
4. **进度条加粗**（如 5px→8~10px）、步骤点过渡更连贯。
5. 乐观渲染的初始 queued 值别太高（如从很低起步平滑涨），减小"跳"感。

### 采集（`collect.html`）
6. 给采集状态区加一个**可视化进度条**（阶段未知用 indeterminate 流动动画）+ 阶段文案（解析链接→拉取详情→提取评论/文案），替代纯文字计时。

### 一致性
7. 视频与采集（可延伸到图片/配音）尽量用**同一套进度组件/样式**（同色系动画、同粗细、同文案风格），跨类型体验统一。DESIGN.md 配色。

## 边界
- 纯前端优化，**不改后端 phase 语义、不改生成核心**；仍用现有 `/api/gen/job/{id}` 的 phase/status（可选：后端加更细 phase 心跳，但非必须）。
- 别让插值"冲到 100% 却还没完成"——完成(有 result/video_url)前 bar 封顶在如 95%，完成瞬间到 100%。

## 验收标准
1. 视频进度条推进顺滑、不再长时间僵在固定百分比；长阶段有 indeterminate 动画；ETA 不再是假静态；bar 更粗；步骤点连贯。
2. 采集有可视化进度条(+阶段文案)，不再只有纯文字计时。
3. 视频与采集进度组件观感一致、符合 DESIGN.md。
4. 完成前不冲 100%、完成即 100%；失败态清晰；无控制台报错。
