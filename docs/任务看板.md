## 🚦 核心规则：按「冲突组」领，同组同时只能 1 个在做

两个任务只要**改同一个文件**就会撞车（合并冲突/互相覆盖）。所以按文件把任务分成**冲突组**——**同一组里，同一时刻只允许一个任务处于「🔵 进行中」**。不同组的任务可以并行。

| 冲突组 | 涉及文件 | 规则 |
|---|---|---|
| **A · 后端核心** | `server/content_api.py`、`server/content_domains/**` | 组内串行（一次一个）|
| **B · 视频页** | `site/workbench/video.html` | 组内串行 |
| **C · 资产页** | `site/workbench/assets.html` | 组内串行 |
| **D · 认证** | `server/auth_server.py` | 组内串行 |
| **imggen · 作图服务** | `server/imggen_api.py` | 组内串行 |
| **E · 其它前端页** | 某个具体 `workbench/*.html` | 按页面，改同一页才冲突 |
| **F · 独立** | `ci.yml`、`docs/**`、字体、脚本等 | 基本不冲突，可随意并行 |
| **admin · 运营后台** | `server/admin_api.py`、`site/admin/**` | 新建后台服务/页，组内串行 |
| **shell · 全站外壳** ⚠️ | `site/workbench/cloud-shell.js`（全站共享左侧栏/导航） | **排他大组**：改 cloud-shell.js 会触发 `stamp_assets.py` 把**全部 workbench/*.html 的 `?v=` 版本戳都 bump**→与**任何**前端页任务冲突。**占 shell 期间禁止一切前端页(B/C/E/admin)任务并行**；有前端页任务在做时 shell 也不能领。 |

> ⚠️ 有的任务**跨组**（比如"批量生成"同时改 content_api 和 video.html → 占 A+B 两组）。跨组任务要等它占的**所有组**都空闲才能领，做的时候也**锁住这几组**。
>
> 🔒 **锁按「你 PR 实际会改的每个文件」来占，不是按任务名义！** 这是防冲突的命根子。开工前先想清楚要动哪些文件、逐一归组、把**每个**组都锁上；中途要多改一个文件 → 先补锁那个组（补不到就停）。**漏锁去改别人的组 = 违规**：即使锁了 shell 也不能顺手改 video.html（那是 B 组）。审核方会核对「PR 改的文件集 ⊆ 你锁的组」，超出直接打回（#244 就栽在只锁 shell 却改了 B/C/E 四个前端页）。

## 🧭 自助领取流程（agent 自己领，靠「组锁」原子防冲突）

**认领的唯一凭据 = 组锁分支 `lock/<组>`**。创建 git 分支(ref)是**原子操作**：两个 agent 同时抢同一个组锁，只有一个能 push 成功，另一个报错——所以**抢到锁 = 合法认领，抢不到 = 该组已被占**。看板的 🔵 状态只是给人看的镜像，由维护者同步。

**步骤：**
1. 看板挑一个 **🟢 可领** 任务，看它的**冲突组**。
2. **抢组锁**（先列出你 PR **实际要改的所有文件**、逐一归组，对**每个**组 G 逐个抢）：
   ```bash
   git fetch origin                                  # 先同步，确保基于最新 main
   git ls-remote origin refs/heads/lock/<G>          # 先看有没有被占(有输出=被占)
   git push origin origin/main:refs/heads/lock/<G>   # 抢锁：成功=抢到；报错(rejected/exists)=已被别人占
   ```
   - **跨组/多文件任务**要把**每个涉及的组都抢到**；任一抢不到 → 把已抢到的用 `git push origin --delete lock/<组>` 退掉、换别的任务或等。
   - 改 `cloud-shell.js` 必占 **shell 排他组**，且当时不能有任何前端页任务在做（见冲突组表 ⚠️）。
3. **抢到锁后立刻更新本看板该行**：状态改 **🔵 进行中** + 填**领取人**（一并提交，别等维护者——看板要实时反映你已认领）。
4. **基于最新 main 开分支**：`git fetch origin && git checkout -b codex/<任务ID> origin/main`。严格按对应《工单》+《开发手册》/§0 开发（走 PR、只走 ship、禁止直改服务器、署名 kongli）。
5. **交 PR 前必须 rebase 到最新 main（防旧分支回退近期工作，强制！）**：
   ```bash
   git fetch origin
   git rebase origin/main             # 拉平到最新主干，解决所有冲突
   git diff origin/main...HEAD --stat # 自检①：改的文件必须 ⊆ 你锁的组，多一个都不行
   git diff origin/main...HEAD        # 自检②：确认没夹带删除/回退别人近期合并的功能
   ```
   - 这是**防冲突的最后兜底**：哪怕锁漏了，rebase 也会把主干新改动合进来、把冲突暴露出来让你解决。**没 rebase 干净、diff 里含别人的改动 → 别交 PR**（会被直接打回，#240/#244 都栽在没 rebase）。
6. 开 PR（**别开成 draft，做完就 Ready**），把看板该行改成 **🟡 待审**。PR 正文注明**改了哪些文件、锁了哪些组**，方便审核核对。
   - 🚫🚫 **开完 PR 就停下，绝对不要自己合并/merge！** 合并 + 部署 + 上线由**审核 AI** 统一把关。你自己合会**绕过审核、且不会被部署到线上**，只会造成 git 与线上分叉。开完 PR 就等审。
7. **审核 AI 合并上线后**：释放你占的每个组锁 `git push origin --delete lock/<G>`。

> **看板维护分工**：**领取的 agent** 负责改自己那行为 🔵进行中(认领时)/🟡待审(交PR时)；**审核 AI** 负责合并后标 ✅、移入已完成、校正对齐、清理卡死的锁。
>
> **审核 AI 合并前必查三关（任一不过 → 打回，不合并）**：① **分支基于最新 main**（`mergeable_state` 非 behind/dirty；落后就让其 rebase 或用 update-branch 重跑 CI）；② **改动文件 ⊆ 声明锁的组**（没锁的组文件被改 = 越界）；③ **不回退近期合并**（比对关键函数/文件是否被旧版覆盖，如前端安全加载、近期 bugfix）。这三关就是防「旧分支合并把已上线的东西冲掉」。

> **一句话规则：只领 🟢 且能抢到全部组锁的任务；抢不到就换一个或等。** 组锁名 = 组字母：`lock/A`(后端核心) `lock/B`(视频页) `lock/C`(资产页) `lock/D`(认证) `lock/E-<页名>`(其它页) —— F 独立组不用锁。
>
> 查当前被占的组：`git ls-remote origin 'refs/heads/lock/*'`
