# 工单 · 视频生成吞吐优化：提 worker 并发 + 单用户并发限流

> 供其他 agent 独立执行。先读《工单-其他agent实施》§0 +《任务看板》+《生产环境清单与还原手册》。
> **冲突组：A（`server/content_domains/core.py`）+ 运维（`content.env` 的 `CONTENT_JOB_WORKERS` + 重启 content）** —— 抢 `lock/A`。
> 相关：ARCH-DEBT-P2 有界队列+固定 worker（#195/#231）、RESIL-POOL（#286）。

## 背景（2026-07-07 使用日志分析结论）
今天 video 生成中位耗时 22 分钟、最慢 64 分钟。拆解发现：
- **HeyGen 口播生成本身 ~15-20 分钟**（外部固有，改不了）。
- **大头是排队积压**：worker 只有 3（`CONTENT_JOB_WORKERS=3`），每小时最多处理 ~12 个；但今天 12 点一小时涌入 47 个视频（yuanzhi 一人刷 67 个），供需失衡 4 倍 → 后提交的任务在队列里干等几十分钟。
- 服务器资源充足（load 0.87、内存半空），**不是机器瓶颈**。
- **HeyGen 是按量计费**：并发上限宽松、且**加 worker 不增加成本**（成本=视频数×单价，与并发无关），纯赚。3 并发今天全天 0 次 429/并发错误 → 有很大余量。

## 待做

### 1. 提 worker 并发 3 → 6（运维，先做，立竿见影）
- `content.env` 加/改 `CONTENT_JOB_WORKERS=6`（`core.py:176` `JOB_WORKERS = _env_positive_int("CONTENT_JOB_WORKERS", 3)` 会读）。
- `sudo systemctl restart huangque-content` 生效。
- **观察 1-2 小时**：`journalctl -u huangque-content` 看有无 HeyGen `429`/`concurrent`/`rate limit` 或泽龙中转限流；job error 里搜同类信号。
  - 没撞 → 可再提到 8-10（渐进，每档观察）。
  - 撞到 → 回退上一档（改 env + 重启，秒级可回滚）。
- ⚠️ 提 worker 会同时增加对 HeyGen/泽龙中转的并发请求，务必盯限流信号。

### 2. 单用户并发限流（代码，防一人刷爆队列）— `core.py` 建任务处
现状：`core.py` 约 936-952 建任务流程 = 预扣点 → INSERT jobs(pending) → `enqueue_job`。一个用户可无限提交（yuanzhi 今天 67 个），把扩出来的并发又占满，其他用户陪等。
- **在预扣点（`deduct_points`）之前**加检查：查该用户当前 **pending+running** 任务数：
  ```sql
  SELECT count(*) FROM jobs WHERE username=? AND status IN ('pending','running')
  ```
  若 ≥ `MAX_USER_ACTIVE_JOBS`（env，默认建议 **5**），直接返回 429 友好提示 **「您有 N 个任务正在排队/生成，完成后再提交」**，**不扣点、不建 job、不入队**（放在预扣前所以无需退点）。
- 阈值走 env `MAX_USER_ACTIVE_JOBS`（`_env_positive_int` 默认 5），便于调。
- 建议只对**慢任务**（video/tryon/image）限流，或全局限流（简单）；二选一在工单里定，倾向全局简单。
- **管理员/特权账号可豁免**（可选，看是否需要）。

### 3. （可选，另 E-video 工单）前端显示真实队列位置/ETA
- 视频页轮询时展示「排队中(第 N 位) / 预计 ~X 分钟」，让用户知道要等 ~20 分钟而非以为卡死。属前端（B/E-video），可单独出单，本单不含。

## 验收标准
1. `CONTENT_JOB_WORKERS=6` 生效（`ps`/日志确认 6 个 worker 线程），队列处理能力翻倍。
2. 提 worker 后观察期内无 HeyGen/泽龙限流错误（或撞到后已回退并记录安全档位）。
3. 单用户 pending+running 达 `MAX_USER_ACTIVE_JOBS`（默认5）后，第 6 个提交被拒（429 友好提示），**且未扣点**；其它用户不受影响。
4. 限流不误伤正常用户（阈值合理）、不影响已在跑的任务。
5. 无回退近期改动（有界队列 #231、退点幂等 #187 等）。

## 部署与验证
- 代码：`./ship "视频吞吐:单用户并发限流(#...)" server/content_domains/core.py` + 改 `content.env` 的 `CONTENT_JOB_WORKERS=6` + `sudo systemctl restart huangque-content`。
- 后端改动需**部署重启 content**。实测：① 6 worker 生效；② 同一用户连提 6 个，第 6 个被拒且没扣点；③ 观察高峰期排队是否缩短、有无限流错误。
- ⚠️ **别在用户活跃高峰重启**（会打断在跑视频，虽自动退点但体验差——今天就踩过）。选低峰期部署。

> 本工单只做规划，未改动任何文件。worker 提到 6 是起步档，稳了可继续提（按量计费无成本上限，只受 HeyGen/泽龙并发限制）。
