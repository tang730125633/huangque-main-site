## 问题（#187）
reaper 超时把 `running` 判失败并**退点**，但**不杀仍在跑的 worker 线程**。该线程稍后：
- (a) 异常路径再调退点 → **二次退点**；或
- (b) 成功后 `UPDATE...SET status='done'` **无条件覆盖**已 error 的行 → 用户**既拿到成片又拿回点数**。

全程无 CAS、退点无幂等键。

## 改动
### 1. 状态迁移一律 CAS（`core.py` run_job / reaper）
- 所有 `running → done/error` 迁移改成条件更新，据 `rowcount` 判断是否抢到迁移权：
  ```sql
  UPDATE jobs SET status='done', result=?, updated_at=? WHERE id=? AND status='running'
  ```
- reaper 判失败同理：`UPDATE...SET status='error'... WHERE id=? AND status='running'`。
- **run_job 写 done/error 前，以 CAS 结果为准**：若 rowcount=0（已被 reaper 接管成 error），**不得覆盖**，且不再走成功后处理。

### 2. 退点 job 级幂等（`points.py` + jobs schema）
- jobs 表加列 `refunded INTEGER DEFAULT 0`（`ALTER TABLE`，兼容老库）。
- 退点前 CAS：`UPDATE jobs SET refunded=1 WHERE id=? AND refunded=0`，**仅 rowcount=1 时真正加回点数**，否则跳过（已退过）。
- reaper 退点、异常退点都走这一条，保证**最多退一次**。

### 3. 时序正确性
- reaper 与 worker 谁先抢到 `running→error/done` 谁定终态；败者放弃写状态、且不触发各自的副作用（退点/入库）。
- 退点只在终态确实是 error 且 refunded CAS 成功时发生。

## 边界
- 只改状态机与退点幂等，不改生成核心/各能力逻辑。
- schema 变更要幂等（列已存在则跳过），别把老库刷坏。

## 验收标准
1. 同一 job 无论 reaper 超时 / worker 成功 / worker 异常如何交错，**点数最多退一次**。
2. 已被 reaper 判 error 的行，**不会被后到的 done 覆盖**（不会既出片又退点）。
3. 补**并发/幂等单测**：模拟 reaper 与 worker 竞态、重复退点，断言点数与终态正确。
4. `py_compile` 通过；老库 ALTER 兼容；content health 正常。

## 部署与验证

- 实测：构造一个超时 job，确认退点一次、终态不被覆盖。
