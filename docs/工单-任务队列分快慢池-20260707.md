# 工单 · 任务队列分快慢池，别让视频堵死作图

> 供其他 agent 独立执行。先读《工单-其他agent实施》§0 +《任务看板》+ `DESIGN.md`。
> **冲突组：A（`server/content_domains/**`）** —— 抢 `lock/A`。纯后端 core.py 改动。

## 背景
用户反馈"作图/出视频要等很久才看到结果，但后台其实早生成好了"。查了服务器真实任务时间线，找到根因：`server/content_domains/core.py` 里**所有任务类型（图片/视频/音频/换装/文案）共用同一条固定 `CONTENT_JOB_WORKERS`(=6) worker 的 FIFO 队列**。视频类任务（video/tryon/xiaole_video）上游耗时动辄 3-25 分钟，只要有几个视频任务在跑，就能把全部 worker 占满，后面排队的作图任务（本来 15-30 秒能出）也得干等 worker 空出来。

**证据**：实测直接调用生成函数（绕开队列）文生图只要 15-30 秒；但真实任务 #1014（作图）从提交到完成耗时 1894 秒(31.5分钟)，同期有 4 个视频任务（#1010/#1013/#1015/#1016）在跑，明显是排队卡住而非生成本身慢。

## 改动
`server/content_domains/core.py`：
- 新增 `SLOW_JOB_KINDS = {"video", "tryon", "xiaole_video"}` 常量
- 新增 `_fast_job_queue`（与原 `_job_queue` 并列），`enqueue_job(job_id, kind=None)` 加 `kind` 参数，按 `kind in SLOW_JOB_KINDS` 决定进哪条队列（`kind` 缺省时查库兜底，用于重启恢复场景）
- `_job_worker_loop(q)` 加队列参数，`start_job_workers()` 分别为两条队列起 `JOB_WORKERS`(慢，沿用现有 env `CONTENT_JOB_WORKERS`，默认3/线上已调6) 和新增 `FAST_JOB_WORKERS`(快，新 env `CONTENT_FAST_JOB_WORKERS`，默认3) 个线程
- `_recover_pending_jobs` 查询补上 `kind` 字段一起传给 `enqueue_job`，重启恢复时也按 kind 分流
- `/api/gen/health` 顺带暴露 `fast_job_workers`，方便运维观测

## 已验证
写了个独立脚本，用假 handler（video 睡 2 秒模拟慢任务，image 睡 0.2 秒模拟快任务），先提交 3 个 video 任务塞满慢队列，紧接着提交 1 个 image 任务：**image 任务在 0.21 秒内完成**，完全不受排在慢队列里的 3 个 video 任务影响（换成旧的单队列逻辑，image 得排在 3 个 video 后面，至少等 6 秒+）。

## 验收标准
1. 提交视频任务后马上提交作图任务，作图任务不应该被视频任务排队卡住（用上面同款测试思路验证）。
2. 正常单独提交视频/作图/音频，各自功能不受影响，扣点/退点逻辑不变。
3. 服务重启后（`_recover_pending_jobs`）待处理任务能正确按 kind 分流到对应队列，不会全部挤到一条队列。
4. `/api/gen/health` 能看到 `job_workers` + `fast_job_workers` 两个数。

## 部署与验证
- 只改 `server/content_domains/core.py` → ship 到 `/home/ubuntu/content-api/content_domains/`，重启 `huangque-content`。
- ⚠️ 部署后建议观察一段时间的真实任务时间线（同上面的 SQL 查询方法），确认作图类任务耗时明显回落到几十秒量级，不再被视频任务拖到几分钟/几十分钟。
- 可选：视线上负载情况，后续通过 `CONTENT_FAST_JOB_WORKERS` env 调大快队列 worker 数（当前默认3，跟慢队列的6独立）。
