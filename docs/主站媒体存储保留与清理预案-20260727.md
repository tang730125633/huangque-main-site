# 主站媒体存储保留与清理预案

> 状态：只读调研完成，尚未执行清理、部署或 COS 生命周期配置  
> 调研时间：2026-07-27  
> 生产服务器：腾讯云 `dapeng-server`  
> 原则：GitHub 是代码正本；不得直接在生产服务器编写清理逻辑；任何物理删除必须先预览、可追溯、可恢复。

## 1. 普通人结论

现在不能直接设置“每天删除两天前所有图片和视频”。服务器上的媒体文件混合了四类数据：

1. 已经上传 COS 的本地副本；
2. 只存在服务器本地、尚未迁移到 COS 的正式作品；
3. 用户以后仍可能复用的形象、参考图、音频和项目素材；
4. 生成过程中遗留、数据库已经不再引用的中间文件。

只有第 4 类可以作为第一阶段的自动清理对象。其他文件必须先确认 COS 对象可读、数据库引用完整，并确保后续生成不再依赖本地文件。

数据库引用分析：

- 超过 2 天的 43.70 GiB 文件中，约 33.78 GiB 仍被任务或资产数据库引用。
- 约 9.92 GiB 没有在当前数据库媒体字段和任务 JSON 中找到引用，是第一批“候选清理对象”，但仍需清单复核和隔离观察。
- 约 10.40 GiB 本地文件同时具备 COS 地址，其中包含可考虑清理的本地副本，也包含可能继续参与生成的输入，不能一刀切。
- 超过 2 天且已经软删除的视频中，约 0.97 GiB 有 COS 副本、约 0.62 GiB 仍是本地链接。
- 超过 2 天的已完成视频中，约 9.01 GiB 仍只使用本地地址，删除后用户会立即无法下载。
- 当前有 1 条超过 2 天仍标记为 `running` 的视频任务，必须先判定终态，不能由清理器处理。

### 2.3 现有删除能力

当前系统已经支持用户在资产库点击删除，但只是软删除：

- 图片：`jobs.deleted=1`
- 音频：`audio_assets.deleted=1`
- 视频：`video_assets.status='deleted'`
- 统一资产：`assets.deleted=1`

软删除只让资产从页面消失，不会删除本地文件，也不会删除 COS 对象。当前 COS 助手只有上传、取地址能力，没有应用级 COS 删除闭环。

### 2.4 现有自动清理

- 未发现黄雀媒体清理的 cron、systemd timer 或生命周期脚本。
- `COS_DELETE_LOCAL` 未显式开启，代码默认上传后保留本地文件。
- COS 已配置并用于新媒体产出，但历史数据中仍有大量本地链接。
- 暂时无法确认 COS 总容量、对象数量、生命周期、版本控制和费用告警；这些需要 CAM 子用户或主账号控制台权限。

## 3. 数据分类与建议保留期

| 数据类型 | 示例 | 第一版策略 |
|---|---|---|
| 临时/中间文件 | 静音副本、压缩参考视频、生成工作目录 | 完成或失败 48 小时后进入隔离区，隔离 7 天后物理删除 |
| 数据库未引用文件 | 找不到任何任务或资产引用的旧文件 | 48 小时后列为候选；先隔离，不直接删除 |
| 用户已软删除作品 | 用户主动从资产库删除 | 保留 7 天撤销窗口；确认无项目引用后删除本地与 COS |
| 已完成且有 COS 的最终成品 | 图片、音频、视频成品 | 本地至少保留 7 天；确认 COS 可读且无需本地复用后再删本地副本 |
| 已完成但只有本地链接的成品 | 历史作品 | 先迁移 COS、更新数据库、抽样验证，再删本地 |
| 用户输入和可复用素材 | 形象、参考图、参考视频、个人音色 | 禁止按文件年龄删除；跟随资产/项目生命周期 |
| 短剧项目素材 | 分镜、角色、配音、合成版本 | 禁止按文件年龄删除；按项目依赖图处理 |
| 数据库 | 用户、积分、任务、资产记录 | 不纳入媒体清理；独立备份和保留策略 |
| 内部测试账号作品 | 明确标记为内部测试的数据 | 可设 2～7 天，但必须依赖账号标签/白名单，禁止按用户名猜测 |

## 4. 推荐的最小安全方案

### 阶段 A：先控制服务器本地增长

新增一个数据库感知的清理器，只处理“超过 48 小时、任务已终止、数据库完全未引用”的文件。

必须具备：

1. `--dry-run` 默认模式，只输出候选清单和预计释放空间；
2. 排除所有 `queued/running` 任务；
3. 排除数据库所有 `file/url/payload/result` 字段能找到的文件；
4. 排除形象、音色、短剧项目和用户上传素材；
5. 再次检查文件修改时间，避免扫描后文件被任务更新；
6. 每次最多处理固定容量，建议第一版上限 5 GiB；
7. 不直接删除，先移动到同磁盘隔离目录；
8. 保存 JSONL 清单：原路径、大小、修改时间、原因、执行批次；
9. 隔离 7 天后才物理删除；隔离期间可按清单恢复；
10. 运行前后记录磁盘、服务健康和 `/api/gen/health`。

建议定时：每天凌晨执行一次即可，不需要每两天才运行；“48 小时”是文件保留门槛，不是 timer 周期。

第一阶段只覆盖约 9.92 GiB 的未引用旧文件候选，不处理仍被数据库引用的 33.78 GiB。

### 阶段 B：补齐用户删除闭环

把现有软删除扩展为两阶段删除：

1. 用户点击删除时继续软删除，写入 `deleted_at`；
2. 7 天内允许恢复；
3. 清理器确认没有其他资产、项目或任务引用；
4. 删除服务器本地副本；
5. 使用 COS 对象键删除对应对象；
6. 写入 `purged_at`、删除批次和结果，数据库保留最小审计墓碑；
7. COS 删除失败时不得把数据库标为已完成物理清理，等待下次重试。

### 阶段 C：迁移历史本地成品

针对仍返回 `/api/gen/file/...` 的历史正式作品：

1. 生成迁移清单；
2. 上传 COS；
3. 对 COS URL 做 HEAD/Range 校验；
4. 原子更新数据库 URL；
5. 从网页和小程序抽样播放、下载；
6. 本地保留 7 天后再进入隔离清理。

这一步完成前，不能清理约 9.01 GiB 的本地视频成品。

### 阶段 D：配置 COS 生命周期

拿到 CAM 权限后先查看，不立即创建全桶规则。禁止对整个 `huangque/` 前缀设置“2 天删除”，否则正式用户作品也会消失。

后续应把新对象按用途分前缀或标签：

```text
huangque/tmp/                 临时文件，可 2～7 天清理
huangque/internal-test/       内部测试，可按测试策略清理
huangque/users/.../final/     用户正式作品，不自动短期删除
huangque/users/.../source/    用户输入，跟随资产/项目生命周期
huangque/deleted/             等待物理清理的逻辑分组
```

只有 `tmp/` 和明确的 `internal-test/` 才适合用 COS 生命周期自动短期删除。正式作品优先转低频存储降低费用，而不是直接删除；具体时间必须与产品用户协议一致。

## 5. 腾讯云告警接入飞书与多维表

### 5.1 已确认的现状

- 腾讯云官方支持把云监控告警直接推送到飞书群机器人。
- 生产服务器已运行腾讯云监控组件 `barad_agent`，并运行 `tat_agent`，具备上报 CVM CPU、内存、磁盘等指标的基础。
- 现有飞书多维表名为「黄雀渠道日报」，当前只有一张「渠道日报」数据表。
- 「渠道日报」已经保存日期、功能、大类、渠道、成功、失败、总数、成功率和点数消耗等字段。
- `/home/ubuntu/hq_bitable_sync_server.py` 已经每 5 分钟同步当天数据，00:10 终算前一天。
- 服务器上的 `base-monitor` 还负责图表辅助记录和 14 天保留，但这部分运行代码当前没有完整进入 Git 正本；扩展前必须先在 Git 分支建立正本，不能直接改服务器。
- 当前 Mac 的 `lark-cli` 用户授权已失效；服务器现有飞书应用授权仍可正常读取「黄雀渠道日报」。实际配置时应复用服务器应用身份，Mac 只在人工建表时重新授权，不让生产任务依赖个人登录态。

### 5.2 推荐架构

使用两条互相独立的通道：

```text
腾讯云告警策略
    ├── 直接推送飞书群机器人 → 人立刻看到触发/恢复通知
    └── 只读 CAM 监控 API → 每 5 分钟同步告警历史到多维表

腾讯云指标 + 服务器本地检查
    └── 每小时写入「云资源快照」→ 趋势、容量和后台复盘
```

不建议把腾讯云通用告警回调直接暴露给主站接口，再由主站写多维表。腾讯云官方说明通用回调目前没有 HTTP 认证机制；直接暴露会形成可被伪造和刷写的公网入口。第一版使用 `DescribeAlarmHistories` 主动拉取告警历史，更安全，也更容易去重。

### 5.3 第一步：创建飞书告警群机器人

由飞书群管理员在电脑端操作：

1. 进入负责开发运维的飞书群。
2. 打开「群设置 → 群机器人 → 添加机器人 → 自定义机器人」。
3. 名称填写「黄雀腾讯云告警」，头像与描述注明用于 CVM、COS、CDN 告警。
4. 复制 Webhook 地址，立即保存到安全密码库；不得发到聊天、Git、截图或普通文档。
5. 安全设置优先使用固定关键词「告警」。腾讯云直接推送不适合使用 IP 白名单；若腾讯云模板不能生成飞书签名，也不要强开签名校验。
6. Webhook 只交给腾讯云通知模板，不写入服务器代码和仓库。
7. 添加完成后发送一条测试告警，确认群里能收到“触发”和“恢复”两种消息。

官方操作参考：[腾讯云：使用飞书群接收告警通知](https://cloud.tencent.com/document/product/248/64168)。

### 5.4 第二步：创建腾讯云通知模板

需要主账号或具备云监控写权限的 CAM 管理员操作：

1. 打开「腾讯云可观测平台 → 告警管理 → 告警配置 → 通知模板」。
2. 新建模板「黄雀生产告警-飞书」。
3. 通知类型勾选「告警触发」和「告警恢复」。
4. 通知周期设置周一至周日、全天。
5. 接口回调选择飞书机器人，填写上一步 Webhook。
6. 普通提示不 @ 全员；磁盘 90%、主机不可达、COS 停服等紧急策略单独使用 @ 全员模板。
7. 保存后先绑定一条低风险测试策略，验证成功再批量绑定。
8. 在飞书群确认消息包含：产品、资源、指标、当前值、阈值、发生时间、状态、策略名和控制台链接。

### 5.5 第三步：建立告警策略

第一版建议阈值如下；上线后根据 7～14 天基线调整，避免误报：

| 产品 | 指标/事件 | 提示 | 严重 | 紧急 |
|---|---|---:|---:|---:|
| CVM | 磁盘使用率 | ≥70% 持续10分钟 | ≥80% 持续5分钟 | ≥90% 持续1分钟 |
| CVM | CPU 使用率 | ≥80% 持续10分钟 | ≥90% 持续5分钟 | - |
| CVM | 内存使用率 | ≥80% 持续10分钟 | ≥90% 持续5分钟 | - |
| CVM | 主机 Ping 不可达、磁盘只读、异常关机 | - | - | 立即告警 |
| COS | 5xx 或上传失败 | 5分钟出现异常 | 错误率明显上升 | 连续不可读写 |
| COS | 4xx | 以基线判断异常增长 | 可能存在权限/盗链问题 | - |
| COS | 存储容量和日增长量 | 每日快照 | 超出月预算趋势 | - |
| CDN | 回源失败率 | ≥1% 持续5分钟 | ≥5% 持续5分钟 | ≥20% 持续1分钟 |
| CDN | 5xx 占比 | ≥1% 持续5分钟 | ≥5% 持续5分钟 | - |
| CDN | 流量/带宽 | 超过近7日同时间段2倍 | 接近费用封顶 | 触发流量封顶 |
| CDN | 缓存命中率 | <70% 持续15分钟 | <50% 持续10分钟 | - |

注意：COS 存储容量增长通常更适合作为日快照和预算趋势，不应只依赖瞬时告警；CDN 4xx 也可能包含正常的鉴权失败，必须先观察基线再定阈值。

### 5.6 第四步：为自动同步建立独立 CAM 机器账号

人工登录账号和机器 API 账号必须分开：

1. 人工 CAM 子用户只用于控制台查看，开启 MFA，不创建 API 密钥。
2. 另建一个仅编程访问的机器子用户，例如 `huangque-monitor-sync`。
3. 机器用户不允许控制台登录，不授予 AdministratorAccess。
4. 第一版绑定：
   - `QcloudMonitorReadOnlyAccess`
   - `QcloudCVMReadOnlyAccess`
   - `QcloudCOSReadOnlyAccess`，后续最好进一步收窄到目标桶
   - `QcloudCDNReadOnlyAccess`
5. 不授予删除 COS、修改 CDN、关机、重启、重装、修改安全组或创建告警策略的权限。
6. SecretId/SecretKey 只放服务器 `/etc/huangque/tencent-monitor.env`，权限 `root:root 600`，由 systemd `EnvironmentFile` 加载。
7. 密钥不得放入 `.hq_feishu.env`、Git、日志、飞书多维表或命令历史。
8. 每 90 天轮换一次；轮换时先验证新密钥，再撤销旧密钥。

腾讯云监控只读预设策略及产品只读策略可参考：[云产品权限授予](https://cloud.tencent.com/document/product/248/45428)。

### 5.8 第六步：扩展现有同步程序

必须从 Git 分支开发并通过 PR，不得直接修改 `/home/ubuntu/base-monitor/`：

1. 复用 `scripts/hq_bitable_sync_server.py` 的飞书认证和 Base API 助手，不再写第二套 token 逻辑。
2. 新增腾讯云只读采集模块：
   - 每 5 分钟调用 `DescribeAlarmHistories`，拉取最近 15 分钟告警并按 `AlarmId` upsert。
   - 每小时调用 `GetMonitorData`，写 CVM/COS/CDN 指标快照。
   - 同时从本机读取 `df`、systemd 服务状态和健康接口，补充主站应用数据。
3. 同一个告警恢复后更新原记录，不新增重复行。
4. 保存同步游标和最近成功时间，API 短暂失败时下次补拉。
5. 多维表写入失败不影响主站服务；记录日志并发送一次飞书群告警，设置冷却避免刷屏。
6. 使用 `flock` 防止 cron 重入；单次超时建议 60 秒。
7. 告警事件保留 180 天；小时快照保留 90 天，长期只保留日聚合。
8. `GetMonitorData` 有 API 调用计费规则；按小时、少量指标拉取通常远低于每月免费请求量，但上线后仍需看账单。

### 5.9 第七步：验收

依次完成四类演练，演练后恢复配置：

1. 把磁盘测试阈值临时调到当前值以下，确认飞书群收到触发消息。
2. 恢复阈值，确认群里收到恢复消息，且多维表同一 `AlarmId` 更新为已恢复。
3. 停止一个无业务影响的测试服务，确认「主站应用」快照标记异常；不要停止生产核心服务做演练。
4. 运行多维表同步自检，确认「云资源快照」出现 CVM 磁盘、COS容量和 CDN 指标。

验收标准：

- 告警触发到飞书群不超过 5 分钟；
- 告警进入多维表不超过 10 分钟；
- 恢复状态能更新原记录；
- 同一告警不会重复刷表；
- 飞书或腾讯云 API 失败不会影响主站生成、登录和支付；
- 日志和多维表中没有 SecretId、SecretKey、飞书 App Secret 或机器人 Webhook。

## 7. 清理预案两小时执行窗口建议

这两小时只做第一阶段上线和 CAM 配置，不进行全量 COS 删除。

| 时间 | 操作 |
|---|---|
| 0～20 分钟 | CAM 子用户、MFA、只读权限、告警接收人和 COS/CDN/CVM 现状截图 |
| 20～40 分钟 | 核对 COS 生命周期、版本控制、容量、费用和近 30 天增长 |
| 40～70 分钟 | 在代码分支运行清理器 `--dry-run`，生成候选清单，不删除 |
| 70～90 分钟 | 人工抽查候选文件及数据库引用，确认排除用户资产和进行中任务 |
| 90～105 分钟 | 小批量移动不超过 1 GiB 到隔离区，验证网页、小程序、生成和下载 |
| 105～120 分钟 | 配置磁盘/COS/CDN 告警，记录批次，决定是否启用每日 timer |

首次运行不要直接释放 39 GiB。先隔离不超过 1 GiB，观察 24～48 小时；无问题后再把单批上限提高到 5 GiB。

## 8. 故障与回滚

| 现象 | 动作 |
|---|---|
| 用户资产打不开 | 立即停用 timer；按批次清单恢复隔离文件；检查数据库 URL |
| COS 地址 403/404 | 不删本地；检查对象权限、签名和 CDN 回源 |
| 清理时服务负载升高 | 停止本批；降低每批数量并使用低优先级执行 |
| 磁盘超过 80% | 优先处理已确认无引用的中间文件和旧部署备份，不碰用户正式作品 |
| 磁盘超过 90% | 暂停媒体生成，先扩容或执行已经审核过的清理清单 |
| COS 删除失败 | 保留数据库墓碑并重试，不把任务标记为清理完成 |
