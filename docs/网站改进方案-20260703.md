# 黄雀主站改进方案（2026-07-03）

> 面向**功能完整性 / 用户体验 / 安全 / 性能 / 工程质量**的评估，与《结构优化方案》（偏代码结构）互补。
> 每条都标了依据文件，按优先级 P0（风险/阻断）→ P1（高价值）→ P2（打磨）排列。

---

## P0 · 风险与阻断（尽快）

### P0-1 动作模仿后端只在服务器、git 里没有 —— 随时会被覆盖
- **现象**：`video.html` 的动作模仿前端已在 git，但 `content_api.py` 的 `mode='motion'` + `generate_heygen_motion_video()` 后端**只存在于线上服务器**，git main 没有。
- **风险**：任何人用 git 部署 `content_api.py`（走 ship 或部署旧 PR）都会把整个动作模仿后端删掉，功能立刻挂。今天已发生过一次（我部署死代码时短暂覆盖，Codex 重写回来）。
- **对策**：把线上带动作模仿的 `content_api.py` 回收进 git（开 PR），之后 `--bless` 刷新漂移基线。**在回收前禁止任何人 ship 部署 content_api。**

### P0-2 昂贵生成接口无限流 / 防滥用
- **依据**：`content_api.py` 全文无 rate-limit / 频控（仅点数预扣）。作图、视频（HeyGen 真金白银）、语音克隆都只靠点数门槛。
- **风险**：一个泄露的 token 或恶意用户可短时间狂刷 HeyGen/OpenAI，烧钱烧配额；点数失败退还机制还可能被反复触发探测。
- **对策**：加**每用户 + 每 IP 的滑动窗口频控**（如每分钟 N 次生成），对 video/image/clone 这类高成本接口单独设更严阈值；并发也设上限。

### P0-3 凭证与登录面（延续结构方案，未完成）
- leadgen 口令仍是被泄露的旧值（git 已清、服务器待换，需通知团队 + 同步 Mac worker）。
- `worker/server_worker.py` 青果代理 key `QG_KEY=55DC9F7E` 硬编码。
- 服务器仍开 SSH 密码登录，建议改密钥、关密码认证。

## P1 · 高价值改进

### P1-1 缓存戳版本漂移 → 视频页可能加载旧外壳
- **依据**：13 个页面 `cloud-shell.js?v=15`，唯独 `video.html` 还是 `?v=14`。
- **后果**：视频页用户可能加载到旧版共享外壳，行为不一致（导航/登录态 bug）。
- **对策**：立即统一 v=15；根治方案是构建时按文件 hash 自动注入戳，杜绝手动漏改（见结构方案 P1-5）。

### P1-2 导航里的「死胡同」入口
- **依据**：侧栏 10 个入口中，**设置**（`settings.html`）是"敬请期待"stub；`assets.html` 有多张"敬请期待"占位卡。
- **后果**：用户点「设置」得到空页面——而设置往往是找"改密码/团队/计费/退出"的地方，体验断裂。
- **对策**：优先把**设置页**做出来（账号资料 / 改密码 / 团队成员 / 计费入口 / 退出登录）——目前改密码、团队管理无处可去。占位卡要么补内容、要么先从导航隐藏，别露"敬请期待"。

### P1-3 全站依赖 Google Fonts（大陆访问慢/被墙）
- **依据**：14 个页面引用 `fonts.googleapis.com` / `fonts.gstatic.com`（Noto Sans SC + JetBrains Mono）。
- **后果**：面向大陆用户，字体请求经常慢或超时 → 首屏字体闪烁（FOUT）、加载变慢，甚至拉长白屏。
- **对策**：**自托管字体**（把用到的字重子集化后放本站 `/assets/fonts/`），去掉外部依赖；中文字体建议按常用字子集化控制体积。

### P1-4 点数逻辑跨进程直写 auth 的 users.db
- **依据**：`content_api.py` 直接读写 `/home/ubuntu/auth-service/users.db` 做扣/退点。
- **风险**：两个服务并发写同一 SQLite，锁竞争/竞态；扣点与退点非原子。
- **对策**：点数收敛为 auth 服务的 HTTP 接口（扣/退/查），content-api 只调接口，单写者。

### P1-5 生成失败的用户反馈与可观测性
- **依据**：后端有 77 处 `raise`（中文报错），前端多用 toast 呈现；但无统一错误码、无失败率监控。
- **对策**：给关键接口加结构化错误码 + 简单埋点（成功/失败/耗时），失败率异常可复用现有飞书告警。

## P2 · 体验打磨与工程

- **P2-1 移动端密度**：页面信息密度高（assets 934 行、collect 885 行），需系统过一遍窄屏断点（侧栏抽屉已有，但表单/网格需逐页核对）。
- **P2-2 新用户引导**：主流程「获客→爬取→作图/视频/音频→资产」缺首次引导；灵感页(inspiration)可承担 onboarding。
- **P2-3 示例/占位数据**：多页内置"仙颜美容"示例文案，需确认登录后是否被真实数据替换，避免新用户看到他人示例。
- **P2-4 无业务测试 + CI 仅静态检查**：CI 只跑 `ci_validate.py`；建议加 `py_compile` 全量 + 关键函数单测（这次的"双 gen_image 定义"就能被 py_compile 拦）。
- **P2-5 content_api 单体**：~2000 行单文件，按域拆分（image/audio/video/leads/points）提升可维护性（见结构方案 P1-1）。
- **P2-6 服务器混合负载**：主站服务与 Dify/OpenClaw 沙箱同机，给关键 systemd 服务加 `MemoryMax` 防互相拖垮。
