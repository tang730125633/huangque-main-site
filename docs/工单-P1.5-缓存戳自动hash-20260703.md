# 工单 · P1-5 缓存戳自动 hash（根治手动漏页）

> 供其他 agent 独立执行。开工前先读《工单-其他agent实施-20260703》§0 公共上下文
> （仓库/分支PR/ship/DESIGN.md/漂移哨兵/**禁止服务器直改**）。

## 目标与价值
工作台页面用 `cloud-shell.js?v=N` 做缓存刷新。现在靠**人手逐页 bump** 版本号，必然漏页（实锤：video.html 曾被漏在 v=14，其余 13 页已 v=15，见《验收记录-T2-缓存戳》）。**改为按文件内容 hash 自动生成戳 + CI 强制校验**，从此不再手动、不再漏页。

## 关键约束（务必遵守，否则会误伤漂移哨兵）
本仓库有**每日漂移哨兵**比对"git ↔ 线上"，要求两者一致。因此**戳必须落在 git 里**（源码即真相），由脚本生成、CI 校验，`ship` 照常部署 git 内容。
> ❌ **不要**采用"ship 部署时改写线上 HTML 的戳"——那会让线上 ≠ git、hash 一变哨兵就持续误报。**戳只在 git 中生成，不在部署时动。**

## 现状（已核实）
- 14 个 `site/workbench/*.html` 引用 `cloud-shell.js?v=15`（当前全一致）。
- CI = `.github/workflows/ci.yml`（跑 `scripts/ci_validate.py`）。
- 另有 `cloud.css?v=8`、`cloud.js?v=8` 等（本工单先只治 `cloud-shell.js`，其余可后续同法扩展）。

## 方案（脚本生成 + CI 强制）
1. **新增脚本** `scripts/stamp_assets.py`（零依赖，仅标准库）：
   - 计算 `site/workbench/cloud-shell.js` 内容的短 hash（如 md5 前 8 位）。
   - 把所有 `site/workbench/*.html` 里的 `cloud-shell.js?v=...` 重写为 `?v=<hash>`。
   - 两种模式：
     - 默认：就地重写（供开发者改完 cloud-shell.js 后运行）。
     - `--check`：只校验、不写；若有任一页面的戳 ≠ 当前 hash，则**非零退出**（给 CI 用）。
2. **CI 加校验**：`.github/workflows/ci.yml` 增一步 `python scripts/stamp_assets.py --check`。谁改了 cloud-shell.js 却没跑 stamp、导致戳过期，**CI 直接失败拦住**。
3. **首次落地**：运行一次 stamp，把 14 页的 `?v=15` 统一换成当前 hash 值（本 PR 内提交），此后自动维护。

## 边界与注意
- **纯工程改动**：加脚本 + CI 步骤 + 一次性把 `?v=15` 换成 hash；不改页面任何其它行为。
- 戳值会从 `v=15` 变成一串 hash（如 `?v=a1b2c3d4`）——属预期。
- 本工单会**改到全部 workbench 页面**（重写戳），故**与任何正在改 workbench 页面的工单冲突**（如 F4 改 video.html）。**须在那些工单合并后、无并发改页面时再做**，避免撞车。

## 验收标准
1. 改动 `cloud-shell.js` 内容 → 跑 `python scripts/stamp_assets.py` → 14 页 `?v=` 全部自动更新为**同一个新 hash**。
2. 不跑 stamp 就想合 → CI `--check` 步骤失败、PR 被拦。
3. 落地后全站 `cloud-shell.js?v=` 一致且等于当前文件 hash；`git` 与线上一致（漂移哨兵不报）。
4. 页面功能与现状无差异。

## 部署与验证
- 主要是脚本 + CI + 一次性戳更新，**需 ship 一次让线上同步新戳**：`./ship "P1-5 缓存戳自动hash落地" site/workbench/`（把更新了戳的页面推上线；ci.yml/scripts 随 git 生效无需部署）。
- 上线后：全站戳一致；改 cloud-shell.js 不跑 stamp 时 CI 会红；确认漂移哨兵无新增告警。

> 本工单只做规划，未改动任何文件。建议排在无并发改 workbench 页面的空档执行。
