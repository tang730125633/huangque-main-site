## 安全问题
`POST /api/auth/change_password`：
1. **只要 token 有效就能改密码、不需要旧密码**——拿到用户浏览器 token 的人可直接改掉其密码。
2. **改密后旧 token 仍有效**——已泄露/其它设备的旧登录态没被踢下线，用户以为"改了密码就安全"，实则旧 token 还能用。
3. `Authorization: bearer <token>`（小写）被判 401，`Bearer` 才认——大小写敏感。

## 要修
### 后端 `server/auth_server.py`
1. **改密要旧密码**：`change_password` body 改为 `{old_password, new_password}`；先校验 `old_password` 正确，再改。旧密码错 → 401/400 明确提示。
2. **改密后失效旧 token**：改密成功后清理该用户**已签发的 token**（更安全：清空该用户所有 token，要求重新登录；至少删除除当前外的其它 token）。这样旧设备/泄露 token 立即失效。
3. **Authorization 大小写不敏感**：解析 `Bearer/bearer/BEARER` 都认（token 提取处忽略大小写）。

### 前端 `site/workbench/settings.html`（配合后端改动）
- T5 的改密表单目前**只有新密码**（因旧后端不要旧密码）。FB7 后端要旧密码了 → 前端**加"当前密码"输入框**，随 `old_password` 一起提交。
- 改密成功后按新规则处理登录态（若清了 token → 提示重新登录、跳登录页）。

## 边界
- 只改 auth 的 change_password/token 校验 + settings 改密表单；不动注册/登录/登出主流程（审计确认它们正常）。
- 改完同步 API 文档（change_password 需旧密码 + 改密后登录态规则）。

## 验收标准
1. 改密码必须传对 `old_password` 才成功；错旧密码被拒。
2. 改密成功后，改密前签发的旧 token 失效（`GET /api/auth/me` 返回 401）。
3. `Authorization: bearer/Bearer/BEARER` 都能正常鉴权。
4. 设置页改密表单有"当前密码"框，端到端可用；改密后按规则处理登录态。
5. 注册/登录/登出不受影响；`py_compile` 通过、health 200。
