# 泽龙开发服安全部署

`ship-zelong` 只面向 `ssh zelong` 和 `https://zelong.huangquechuanmei.com`，不共用正式服的 `ship`。

## 必须两步执行

```bash
# 实时读取远端 main（只读）
CURRENT_MAIN_SHA="$(git ls-remote --exit-code origin refs/heads/main | awk '{print $1}')"

# AdsPower 本轮已审核基线：先 dry-run，记下 PLAN_ID
./ship-zelong --commit "$CURRENT_MAIN_SHA" --adspower-baseline

# 只有参数与 dry-run 完全相同才能执行
./ship-zelong --commit "$CURRENT_MAIN_SHA" \
  --adspower-baseline --apply --plan <PLAN_ID>
```

`--adspower-baseline` 已锁定本轮审核过的 11 个文件，并且禁止与 `--file` 混用：

1. `site/workbench/banana.html`
2. `site/workbench/video.html`
3. `server/auth_server.py`
4. `server/wxpay.py`
5. `server/content_domains/core.py`
6. `server/content_domains/image.py`
7. `server/content_domains/video.py`
8. `site/assets/cloud/virtual-pay-item-200.png`
9. `server/wechat_virtual_pay.py`
10. `server/content_domains/miniprogram_security.py`
11. `deploy/systemd/huangque-content.service.d/hardening.conf`

`fb59e511c16f11edef1617b07fe6f2160c14e78e` 是这 11 个文件的已审核内容来源，不是永久的部署 HEAD。实际 `--commit` 必须等于实时 `origin/main`；工具再比较这 11 项在实时 main 和审核来源之间是否完全相同。因此，合并本部署工具等无关改动后 main 可以正常前进；但只要 11 个目标文件中有任意一个改变，预设就会 fail closed，必须重新审核。

工具直接从指定 Git commit 读文件，不读未提交工作区。它会用只读 `git ls-remote` 确认该 SHA 就是实时 `origin/main`，从而拒绝过期本地 ref 或未 push commit；但不会自动更新、提交或推送。缺 commit 时应由操作人先明确同步仓库，然后重做 dry-run。

## 白名单和顺序

- 鉴权：`auth_server.py`、微信支付依赖文件。
- 内容：`content_api.py`、`content_domains/*.py`、`tikhub.py`、`func_names.py`。
- 静态站：`site/` 中明确列出的单个文件；资源先于 HTML 安装。
- systemd：只允许 `huangque-auth` / `huangque-content` 的 unit 和 `.conf` drop-in；改动后必须 `daemon-reload`。
- 服务只可重启 `huangque-auth` 和 `huangque-content`，其他单元不在该工具权限内。

## 备份、验证和回滚

每次执行前会在 `/home/admin/huangque-deploy-backups/<RUN_ID>/` 保留：

- 远端原文件，原本不存在的文件记为 `MISSING`；
- 文件级 SHA-256 和本次 commit/plan；
- 受影响 SQLite 的 online backup，不直接拷贝 `.db` / WAL。

上传后先做 Python import smoke，然后才重启服务。最后同时检查服务 active、两个健康接口和每个目标文件的 SHA-256。健康接口会在最长 35 秒内重试，容纳 systemd 已 active 但 nginx 上游尚未就绪的短暂 502；超过窗口仍失败才停止且不记录为已完成。

```bash
# 先 dry-run
./ship-zelong --rollback <RUN_ID>

# 再按输出的 PLAN_ID 执行
./ship-zelong --rollback <RUN_ID> --apply --plan <PLAN_ID>
```

普通回滚只恢复本次文件，并且只重启受影响的 auth/content。SQLite 备份不自动覆盖当前库，因为那会删除部署后新产生的测试数据；确实需要数据库回滚时，先停止写入、另行审批，再使用已保留的 online backup。
